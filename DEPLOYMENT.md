# Deploying VideoHub

Two pieces go up: the **NestJS API** as a long-running Node service, and the
**React app** as static files. The database (Neon) and object storage
(Cloudflare R2) are external and free.

## Why Render for the API

The API cannot run as serverless functions, so Netlify and Vercel are out for
that half regardless of preference:

| What the app does | Why serverless breaks it |
| --- | --- |
| `@nestjs/schedule` crons — hourly trending, daily guest-conversation purge | No process stays alive between requests, so the decorators never fire |
| `/api/ai/stream` holds an SSE connection open | Function timeouts cut the stream mid-answer |
| Uploads up to `MAX_UPLOAD_MB` — hundreds of megabytes | Vercel caps a serverless request body at a few megabytes |
| Prisma against Neon | Every cold start opens a new connection; a pool is what stops the pooler running out |

The **static app** is different — it is just files, so Render, Netlify and
Vercel all serve it well. Netlify and Vercel have the stronger CDNs. Keeping
both on Render is simpler (one dashboard, one blueprint, no CORS surprises);
splitting the front end to Netlify is measurably faster for visitors far from
Frankfurt. Either is defensible.

**Region matters more than the host here.** Put the API in **Frankfurt**, beside
the Neon database in `eu-central-1`. Measured from Kigali, one round trip to Neon
costs about a second, and the homepage makes several. Same-region it is a few
milliseconds.

## 1. Prepare the database

Your Neon project already exists. From the Neon dashboard, collect two strings:

- **Pooled** connection (host contains `-pooler`) → `DATABASE_URL`
- **Direct** connection (no `-pooler`) → `DIRECT_URL`

Both must end with `?sslmode=require`. Prisma Migrate needs the direct one; the
running app uses the pooled one.

## 2. Create storage (Cloudflare R2)

`STORAGE_PROVIDER=local` is **refused when `NODE_ENV=production`**, deliberately:
Render's free disk is wiped on every deploy, so uploads and mirrored video would
disappear. R2's free tier gives 10 GB and charges nothing for egress, which is
what you want when the payload is video.

1. Cloudflare dashboard → **R2** → **Create bucket**, name it `videohub`.
2. **Manage R2 API Tokens** → create a token with **Object Read & Write**.
   Copy the Access Key ID and Secret Access Key — the secret is shown once.
3. Note your **S3 API endpoint**: `https://<account-id>.r2.cloudflarestorage.com`
4. Bucket → **Settings** → **Public access** → enable an `r2.dev` subdomain (or
   attach a custom domain). That URL becomes `STORAGE_PUBLIC_URL`.

## 3. Deploy from the blueprint

1. Push `main` to GitHub.
2. Render dashboard → **New** → **Blueprint** → pick the `VideoHub` repo.
   Render reads [`render.yaml`](render.yaml) and proposes two services.
3. Fill in the variables marked `sync: false` on **videohub-api**:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | Neon **pooled** string |
   | `DIRECT_URL` | Neon **direct** string |
   | `WEB_ORIGIN` | the web service URL, e.g. `https://videohub-web.onrender.com` — no trailing slash |
   | `STORAGE_BUCKET` | `videohub` |
   | `STORAGE_ENDPOINT` | `https://<account-id>.r2.cloudflarestorage.com` |
   | `STORAGE_ACCESS_KEY` | R2 access key id |
   | `STORAGE_SECRET_KEY` | R2 secret |
   | `STORAGE_PUBLIC_URL` | your `r2.dev` or custom-domain URL |

   `JWT_SECRET` and `JWT_REFRESH_SECRET` are generated by Render. Boot refuses
   the placeholder value from `.env.example`, so do not paste it.

4. On **videohub-web**, set `VITE_API_URL` to the API URL plus `/api`, e.g.
   `https://videohub-api.onrender.com/api`.

   This is compiled into the bundle, so **changing it later needs a rebuild**,
   not a restart.

5. **Apply**. The API build runs `prisma migrate deploy`, so the schema is
   created on first deploy.

### The chicken-and-egg on URLs

`WEB_ORIGIN` and `VITE_API_URL` each name the other service, which does not
exist until the first deploy. Deploy once, copy both URLs from the dashboard,
set the two variables, then redeploy. The API will reject browser requests until
`WEB_ORIGIN` is right — CORS failures in the console are the symptom.

## 4. Seed and fill the catalogue

From your machine, pointed at the production database. Set `DATABASE_URL` and
`DIRECT_URL` to the Neon strings for the length of the command:

```bash
npm run db:seed --workspace=@videohub/api
```

That writes the genres, categories and — if `SEED_ADMIN_EMAIL` and
`SEED_ADMIN_PASSWORD` are set — an admin. Otherwise register through the UI and
promote yourself:

```bash
npm run db:make:admin --workspace=@videohub/api -- you@example.com
```

Then pull in real video:

```bash
npm run db:sync:catalogue --workspace=@videohub/api -- --curated-only --mirror --mirror-max-mb=200
```

With `STORAGE_PROVIDER=r2` this mirrors into the bucket rather than local disk,
so playback is served from R2's CDN. **The 2.3 GB mirrored during development
lives on your laptop and does not transfer** — this re-downloads it into R2, and
it is slow.

The 200 MB cap is deliberate: it takes the short films and leaves the five
feature-length ones streaming from archive.org, which is the difference between
0.6 GB and 2.3 GB of your free 10. Raise it later for whichever titles turn out
to be worth the space.

## 5. Verify

```bash
curl https://videohub-api.onrender.com/api/health
```

Expect `"status":"ok"` and `"database":"up"`. Then open the web URL and check
the homepage rails, a video page, and `/admin` after signing in.

## Making 10 GB of free storage go far

R2's free tier is **10 GB**, and the whole curated catalogue mirrored is 2.3 GB —
so it fits with room to spare. What eats the budget is not the catalogue, it is
uploads and the handful of very large films.

Measured from the development mirror, the **five longest titles are 1.7 GB, 73%
of the total**, while the other seven together come to 603 MB:

| | |
| --- | --- |
| The General, His Girl Friday, Nosferatu, Night of the Living Dead, Caligari | 1.7 GB |
| the remaining seven | 0.6 GB |

Four things keep you inside the free tier:

1. **Cap what you mirror.** `--mirror-max-mb=200` keeps the short films and
   leaves the feature-length ones streaming from archive.org. Slower for those
   few, but the difference between 0.6 GB and 2.3 GB.
2. **Mirror what people watch, not everything.** An unmirrored title still
   plays; it is only slower. Mirror the homepage rails and the kids section
   first, since those get opened most.
3. **Keep `MAX_UPLOAD_MB` low in production.** The blueprint sets 500. At the
   2 GB development ceiling, three uploads would fill the entire free account.
4. **Pick R2 over S3 or B2 for the egress, not the storage.** All three give
   about 10 GB free, but S3 charges roughly $0.09/GB to serve it. One person
   watching a 400 MB film is 400 MB of egress; a hundred views is 40 GB. R2
   charges nothing for egress, which for video matters far more than the 10 GB.

If you outgrow it: Backblaze B2 also gives 10 GB free and is free to serve
through Cloudflare, and Supabase Storage gives 1 GB — the app already supports
`STORAGE_PROVIDER=supabase`. Beyond that, R2 is about $0.015/GB/month, so
100 GB costs roughly $1.50 a month with egress still free.

## What the free tier actually costs you

**Render free web services sleep after ~15 minutes idle**, and the next request
pays a cold start of roughly a minute while the container boots and Nest starts.
**Neon's free tier suspends too.** Both waking at once makes the first visit
after a quiet spell genuinely slow — a demo link sent to someone who clicks it an
hour later looks broken.

Mitigations, honestly ranked:

1. Upgrade the API to Render's cheapest paid instance. It never sleeps. This is
   the only real fix.
2. Ping `/api/health` every 10 minutes from an external cron. It keeps the
   service awake but burns your 750 free instance-hours faster, and Render's
   terms discourage it.
3. Accept it, and tell people the first load is slow.

Two more free-tier facts worth knowing:

- **No persistent disk.** Everything must live in R2. The blueprint already
  forces this, and boot refuses `local` storage in production so you cannot get
  it wrong silently.
- **Static sites do not sleep.** The front end is always instant; only the API
  cold-starts. So the app will render, then sit spinning on its first request.

## Alternative: front end on Netlify

If you would rather have the stronger CDN:

1. Netlify → **Add new site** → **Import from Git** → the repo.
2. Build command `npm run build`, publish directory `apps/web/dist`.
3. Environment: `VITE_API_URL=https://videohub-api.onrender.com/api`
4. Add `apps/web/public/_redirects` containing `/*  /index.html  200` so deep
   links survive a refresh.
5. Update `WEB_ORIGIN` on the Render API to the Netlify URL, and redeploy the
   API so CORS matches.

The API stays on Render either way.
